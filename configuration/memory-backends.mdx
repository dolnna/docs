---
title: "Choose a Memory Backend for MemOS"
description: "Compare the three MemOS textual memory backends — naive_text, general_text, and tree_text — and learn when to use each one for your deployment."
---

MemOS stores textual memories in one of three backends, each with a different storage engine, retrieval capability, and setup complexity. You choose a backend by setting the `MOS_TEXT_MEM_TYPE` environment variable. The right choice depends on your scale, how much relational structure you need in your memories, and how much infrastructure you want to manage.

---

## Backend comparison

| | `naive_text` | `general_text` | `tree_text` |
|---|---|---|---|
| **Storage engine** | SQLite | Qdrant | Neo4j |
| **Setup complexity** | None | Moderate (Qdrant required) | Higher (Neo4j required) |
| **Scale** | Development, small deployments | Production, large-scale | Production, relational memory |
| **Retrieval** | FTS5 keyword + basic vector | Semantic vector + FTS5 | Graph traversal + vector |
| **Relational memory** | No | No | Yes |
| **Extra services** | None | Qdrant | Neo4j + Qdrant (Community) |
| **Best for** | Getting started, local dev | Most production use cases | Complex agent memory, multi-hop reasoning |

---

## `naive_text` — SQLite, zero setup

`naive_text` uses SQLite for both storage and retrieval. No external services are required. It is the fastest way to get MemOS running and is well suited for development, evaluation, and low-volume deployments.

```env
MOS_TEXT_MEM_TYPE=naive_text
```

Retrieval uses FTS5 full-text search combined with basic vector similarity computed locally. This is sufficient for small memory stores but degrades in precision and speed at large scale.

<Tip>
  Start with `naive_text` when first evaluating MemOS or building a prototype. You can migrate to `general_text` or `tree_text` later without changing your application code.
</Tip>

---

## `general_text` — Qdrant, production-ready semantic search

`general_text` stores memory vectors in [Qdrant](https://qdrant.tech/), a purpose-built vector database. It delivers fast, high-precision semantic search and scales to millions of memory records without performance degradation.

```env
MOS_TEXT_MEM_TYPE=general_text
```

You need a running Qdrant instance before starting MemOS. The quickest way is Docker:

```bash
docker run -p 6333:6333 qdrant/qdrant
```

Then configure your embedder variables so MemOS can create and query the vector collection:

```env
MOS_EMBEDDER_BACKEND=universal_api
MOS_EMBEDDER_MODEL=text-embedding-v4
MOS_EMBEDDER_API_BASE=https://dashscope.aliyuncs.com/compatible-mode/v1
MOS_EMBEDDER_API_KEY=your-api-key
EMBEDDING_DIMENSION=1024
```

`general_text` is the recommended backend for most production deployments. It provides semantic search without the graph infrastructure complexity of `tree_text`.

---

## `tree_text` — Neo4j, relational graph memory

`tree_text` stores memories as a graph in [Neo4j](https://neo4j.com/). Memories are connected by relationships, enabling multi-hop reasoning, causal links, and hierarchical memory structures. This is the most powerful backend for agents that need to understand how memories relate to each other.

```env
MOS_TEXT_MEM_TYPE=tree_text
```

You need a running Neo4j instance. Install [Neo4j Desktop](https://neo4j.com/download/) or run it via Docker:

```bash
docker run \
  -p 7474:7474 -p 7687:7687 \
  -e NEO4J_AUTH=neo4j/your-password \
  neo4j:latest
```

Then configure the Neo4j connection variables:

```env
NEO4J_BACKEND=neo4j-community
NEO4J_URI=bolt://localhost:7687
NEO4J_USER=neo4j
NEO4J_PASSWORD=your-password
NEO4J_DB_NAME=neo4j
```

<Note>
  Use `NEO4J_BACKEND=neo4j-community` unless you have a Neo4j Enterprise license. The community backend uses Qdrant for vector indexing (since Community Edition does not support native vector indexes), so you also need a running Qdrant instance when using `tree_text` with `neo4j-community`.
</Note>

### When to use `tree_text`

Choose `tree_text` when your agent needs to:

- Traverse relationships between memories (e.g., "what decisions led to this outcome")
- Maintain a structured world model with typed relationships between entities
- Deduplicate memories by detecting conflicting nodes in the graph
- Support multi-tenant deployments where users share one Neo4j database with logical isolation via `user_name`

---

## Multi-tenant shared database

Both `general_text` and `tree_text` support multi-tenant deployments where multiple users share one database. Enable shared mode with:

```env
MOS_NEO4J_SHARED_DB=true   # for tree_text
```

In shared mode, each user's memories are isolated by their `user_id`. All reads, writes, and searches automatically filter by `user_id`, so users never see each other's data.

## Reranker options

After the primary retrieval step, MemOS optionally reranks results to improve the final relevance ordering. Configure the reranker independently of the memory backend:

| Value | Description |
|---|---|
| `cosine_local` | Default. Reranks using local cosine similarity computation. Requires no extra service. |
| `http_bge` | Uses an external BGE reranker HTTP service. Provides higher-quality reranking at the cost of an additional service dependency. |

```env
MOS_RERANKER_BACKEND=cosine_local
```

Use `http_bge` only if you have a BGE reranker deployed and need maximum retrieval precision.
